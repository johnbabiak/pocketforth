<h2> Abstraction </h2>

I will start with how I even heard about Forth's in the first place. I am a software engineer, and I recently had the thought that I don't really have a full understanding of how computers work. Sure, I understand how they are supposed to work in theory, and I have even done the hardware section of nand2tetris ([https://www.nand2tetris.org/](https://www.nand2tetris.org/)), but I still could barely tell you what happens from when you push the power button to launching an application. With computers, there is just so much to know. You might know one piece of it, such as how a specific application works, or maybe how a protocol is implemented. At every point, there is a limit to what you understand. Maybe you know how to use the command line tool netcat ([https://netcat.sourceforge.net/](https://netcat.sourceforge.net/)), and so you understand IP addresses, ports, and sockets. You might even know some niche options available for the command. That, however, is just the user perspective. Underneath, there is the application code for netcat. That code relies on OS resources that expose network device drivers. To a user, we have to look down multiple layers to really get a full understanding of what is going on.

This idea can be summed up through the concept of **abstraction**. Basically, instead of having to understand the full system, a user or developer only needs to understand **interfaces** and then a specific layer of the system. An example of an interface is the Linux system call interface. Application developers do not need to know how the Linux `read()` syscall ([https://man7.org/linux/man-pages/man2/read.2.html](https://man7.org/linux/man-pages/man2/read.2.html)) is actually implemented, and instead only need to know how to use it. In this manner, the inner workings of the system call are abstracted away, allowing the user or developer to just focus on what they need to know.

This idea of abstraction and interfaces is super important to how modern computer systems have been designed and implemented. With these techniques, large systems like a computer or the internet can be broken down into bite-sized problems that individual people can work on together. Instead of a single person needing to be an electrical engineer, computer engineer, and computer scientist, the job can be split among multiple people, allowing for specialization.

So, obviously, abstraction is an important and necessary concept that a majority of the tech industry relies on. However, personally, I believe that is also reduces understanding. Specifically, as a user of a system, it is immensely difficult for me to understand everything about how it works. I use Ubuntu Linux on my personal PC, and it would take me countless hours to fully understand the operating system. And, even if I learned everything about the operating system, I would also have to learn about how my actual PC hardware works to have full understanding. I do not believe that, in a reasonable amount of time, I could begin to learn and understand all of that information.

<h2> Simplification </h2>

I am the type of person that enjoys fully understanding systems. An example of this from my personal life is that I am a huge car enthusiast. I am not just satisfied to drive my car without knowing how it works, and so I have done a ton of research into everything automobile in order to understand them. I am by no means an expert, but I have a decent knowledge when it comes to cars. In the same way, I recently wanted to start learning more about just how exactly computers work.

One of the first places I started was with this series: [https://0xax.gitbook.io/linux-insides](https://0xax.gitbook.io/linux-insides). This series is an awesome peek underneath the hood of how a Linux OS/kernel actually boots when you press the power button. I think one of the big things that this series made me realize is just how many steps it takes a modern PC to go through before we actually arrive at a usable state where it can be interacted with. You have to go through a piece of firmware, the BIOS/UEFI, then you have a bootloader which then actually loads the kernel, and then the operating system.

When I was thinking about this, it made me wonder: is there a way to interact with the computer at a more fundamental, simple level? The BIOS/UEFI is firmware that runs directly on top of the hardware. I would like to use the computer at that level! So, I continued my search.

<h2> Discovery </h2>

This led me to search for low-level operating systems, and I landed on this project from Virgil Dupras: [https://collapseos.org/](https://collapseos.org/). Now, I don't know whether society is going to collapse by 2030, but I do just love the idea. An operating system that can run on pretty much any common hardware is pretty cool. When reading about CollapseOS, I found that Dupras mentions the idea of a "Forth" a lot, but I honestly had no idea what that was. Luckily, he has a whole series that guides you through what a Forth is: [https://tumbleforth.hardcoded.net/](https://tumbleforth.hardcoded.net/). This series, at least for me, was seriously eye-opening, and worth a read for anybody interested in computers. Basically, a Forth is a type of firmware that provides an environment for a user to interact directly with a computer on bare-metal. It does this by combining a *compiler*, an *interpreter*, and simple data structures so that a user can define and use *words* that the computer can understand and run. Interaction with the computer is stack-based, so users actually push, pop, and interact with stack values with almost every word that they use.

Reading through Dupras's work, he specifically states that using a Forth doesn't allow someone to just *use* a computer, but rather to *operate* it ([https://duskos.org/who.html](https://duskos.org/who.html)). The idea of this was extremely tantalizing to me, and I wanted to get started right away using a Forth. The first Forth that I found was `gforth`, a Forth that you can use directly in the Linux terminal. However, to me, this was extremely unsatisfying, as it still required a whole operating system to use. So, I continued to search for other options.

<h2> FlashForth </h2>

The Forth that I finally landed upon was **FlashForth** ([https://www.flashforth.com/](https://www.flashforth.com/)). This Forth is basically just a firmware the runs directly on a series of supported microcontrollers. I happened to have an Arduino Mega lying around, and so this Forth seemed perfect for me. I would be able to run **FlashForth** directly on the Arduino, and then talk to it directly over a serial interface. The Arduino actually already has firmware on it, specifically a bootloader ([https://docs.arduino.cc/retired/hacking/software/Bootloader/](https://docs.arduino.cc/retired/hacking/software/Bootloader/)) that is used to program the microcontroller. With Arduinos, the intent is to use the Arduino IDE, write a program, compile it, then send it over to the microcontroller. The bootloader then loads it into memory and runs it. FlashForth, however, replaces this bootloader, and allows direct serial interaction with the Arduino. It also requires a firmware flash in order to get it onto the Arduino which I will cover in my <a href="../01-flashing-forth/">next post</a>.
